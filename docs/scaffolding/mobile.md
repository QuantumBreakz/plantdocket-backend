# PlantDocket Future Mobile Repository Scaffold

**Proposed repository.** `plantdocket-mobile`

**Delivery phase.** Post-MVP. The React Native employee app is a second interface for workflows that have shipped on the website. The [post-MVP roadmap](../mvp/03-post-mvp-roadmap.md#future-mobile-client) owns the decision to start it. The [web MVP scope](../mvp/01-scope.md) applies to the browser product.

## Start criteria and parity

Establish a released web baseline, versioned API contract, policy for native sign-in and approved device connectivity, and a support owner. Select supported Android/iOS versions, framework/toolchain versions, dependency pinning and distribution model at kickoff. Record the exact website release used as the parity baseline.

| Website workflow | Native parity requirement |
| --- | --- |
| Sign-in, workspace and folder access | Use the same named employee identity and effective permissions. Honor expiry, revocation, concealed records and approved site selection. |
| Catalog, revisions and history | Preserve the same current approved revision, revision history and access behavior. A scanned draft stays a draft until final approval. |
| Remarks, review queue and decisions | Reuse the exact revision and step contracts. Keep department eligibility, return reasons, concurrency and final publication rules authoritative in Library. |
| Uploads and downloads | Reuse upload reservations, accepted parts, immutable candidate identity and exact-version download authorization. Preserve state after interruption and visibly handle conflict or expiry. |
| Employee sharing controls | Invite or revoke only where that operation already exists on the website and is authorized. The guest email-verification and download page remains accessible through the browser. |

Track each selected native flow against a released web behavior and a feature or acceptance-case ID. Additional workflows require a separate product decision and a web baseline.

## Auth, network and files

- Terminate native sign-in through a supported account entry for the site. For OAuth-based native sign-in, use an external browser, authorization code with PKCE and a registered callback. Validate the redirect, bind it to pending sign-in state and store long-lived credentials with platform-protected storage. Map the session to the same server-side principal. [OAuth for native apps](https://www.rfc-editor.org/rfc/rfc8252) · [React Native linking](https://reactnative.dev/docs/linking).
- Use the existing versioned business APIs through approved ingress. Select an HTTPS endpoint from deployment-managed configuration and verify private connectivity and trust on real devices. Test direct launch, callback from a stopped or running app, and network interruption. Keep business permissions and viewable revision state with the services. A future transport change follows the same request and approval contracts. [React Native networking](https://reactnative.dev/docs/network).
- Use platform file capabilities to read and write bounded slices. Keep only an opaque user/site-scoped upload reference for resume. On restart, reauthorize, check accepted parts and require access to the same file or matching reselection. Expire partial data and scrub it on logout or site switch. Keep signed URLs and document data out of diagnostics.
- Fetch or renew an exact-version download under current access. Apply the site's device storage and export policy. Confirm a 500 MB case on supported hardware before claiming transfer parity.

## Release and device evidence

1. Publish the parity matrix and pin the backend contract digest. Break the build if generated types drift or a selected workflow loses its released behavior.
2. Run unit and contract tests on PRs. Exercise real devices for native sign-in, certificate trust, network changes, interruption/resume, byte integrity, download selection, approval conflicts and membership revocation.
3. Pair signed app build IDs with the tested API version and site profile. Test the device management or approved distribution path separately for each platform. Record certificate, signing and rollback ownership.
4. Verify the exact workflow against the web baseline and record gaps by feature ID. Keep the existing backend and web release gates for the MVP independent of mobile evidence.

The [backend scaffold](backend.md) owns contracts and deployment. The [web scaffold](frontend.md) owns the baseline browser journey. Use the [feature verification matrix](../delivery/05-feature-verification.md) when a native implementation is approved.
